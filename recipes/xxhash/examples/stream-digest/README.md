# xxhash stream digest

One screen that hashes the same generated bytes with `xxh3_64`, `xxh64`, `xxh32` and the
three things Python already has — `zlib.crc32`, `hashlib.md5`, `hashlib.sha256` — at three
sizes, then feeds the largest payload through the streaming API and checks that it lands on
the same digest. Under that, xxHash's own published test vectors recomputed on the device,
and two demonstrations of what a non-cryptographic hash does not protect you from.

Every payload is generated in the app from a fixed seed rather than bundled, so the same
build produces the same bytes on every device and two phones can be compared with each other
and with the desktop figures below.

What it demonstrates:

- **Where xxhash wins, and by how much.** Measured on an Apple M4 desktop under CPython
  3.14.6 with this app's own `throughput()`, best of three runs per column:

  | MB/s | 1 KiB | 64 KiB | 1 MiB | 4 MiB | 16 MiB |
  | --- | --- | --- | --- | --- | --- |
  | xxh3_64 | 19,761 | 46,113 | 47,502 | 46,281 | 46,485 |
  | xxh64 | 13,317 | 24,283 | 24,102 | 24,603 | 24,533 |
  | xxh32 | 8,414 | 12,275 | 12,301 | 12,287 | 12,348 |
  | crc32 | 14,304 | 41,309 | 40,778 | 42,597 | 42,036 |
  | md5 | 720 | 884 | 886 | 867 | 880 |
  | sha256 | 1,864 | 3,074 | 3,008 | 3,092 | 3,078 |

  15× `sha256` and 53× `md5` at 1 MiB. Read the top two rows as ratios rather than absolute
  rates: above roughly 10,000 MB/s the buffer is being re-read out of cache between batches,
  so those figures measure the machine's cache as much as the algorithm.
- **Where it barely wins, in the row underneath.** `zlib.crc32` is 40,778 MB/s at 1 MiB
  against xxh3_64's 47,502 — a 16% gap, not an order of magnitude — and at 1 KiB `crc32` is
  ahead of `xxh64` and `xxh32` outright. Apple's zlib uses the CPU's CRC32 instructions, and
  a phone may or may not; that is exactly the sort of thing only the device can answer, and
  it is why `crc32` is in the table.
- **What sha256 actually costs.** Not 100×. On this desktop `sha256` runs at 3 GB/s because
  arm64 has SHA-256 instructions, while `md5`, which has no such instructions, is the
  slowest row at 880 MB/s. If your reason for reaching past `hashlib` is "cryptographic
  hashes are slow", the table is the place to check that against the hardware you ship on.
- **That the streaming API agrees with the one-shot call, and what it costs.** The largest
  payload is fed through `xxh3_64().update()` in 64 KiB pieces and the result compared with
  `xxh3_64_intdigest()` of the whole buffer. They match — and the streamed path ran at
  17,691 MB/s against 47,137 one-shot on desktop, **0.38×**, because XXH3's one-shot entry
  point has a fast path the incremental state machine cannot use. `xxh64` shows no such gap
  (23,697 against 24,036 MB/s, measured separately). The trade is worth making anyway for
  the app's own shape — one background worker beside an idle event loop, where `update()`
  frees the GIL every 64 KiB and the one-shot call holds it start to finish. It is not worth
  making for throughput across several threads: at this 64 KiB chunk, four threads hashing
  64 MiB each measured 1.03× the serial rate on desktop, and only reached 3.3× once the
  chunk grew to 1 MiB.
- **That the digest is the same everywhere.** 36 of upstream xxHash's own sanity vectors — 8
  for XXH32, 9 for XXH64, 15 for XXH3-64 and 4 for XXH3-128, chosen to straddle every length
  branch — recomputed here over xxHash's own test buffer, which the app regenerates
  from the two constants in `cli/xsum_sanity_check.c`. Every one was checked value-for-value
  against `tests/sanity_test_vectors.h` at v0.8.2, which itself holds thousands of entries
  per algorithm; the 36 are the subset the app carries. All 36 pass on desktop. These are the
  numbers upstream uses to decide a port is correct, so agreement is the claim that this
  build produces the same bytes as xxHash on any other CPU. Both devices are little-endian,
  so a device run confirms the vectors but cannot by itself demonstrate endianness
  independence.
- **A collision, found on the device, in milliseconds, with both inputs printed.** A seeded
  birthday search over random 32-byte inputs finds two sharing an `xxh32` digest after
  113,202, 39,741 and 16,915 tries for seeds 0, 1 and 2 — 21, 7 and 3 ms on desktop — and the
  line underneath shows the pair: `0041f8654fe2dbcf…` and `354b0d889ffb06bc…` both hash to
  `a47caf1d`. Every one of those values is identical on CPython 3.12 and 3.14, because the
  generator is seeded, so a device that prints different ones is telling you something.
- **The input recovered from the digest.** For an input of exactly four bytes, every step
  XXH32 takes is a bijection on 32 bits, so the function is a permutation and can be run
  backwards with arithmetic instead of search. The app inverts 2,000 digests and reports how
  many came back byte-exact: 2,000 of 2,000, in 2 ms on desktop. Nothing here is a flaw in
  xxHash — it is what "non-cryptographic" means, and it is the reason a seed is not a key.
- **Degrading instead of crashing.** The import of `xxhash` is guarded. Without the wheel the
  header turns red and names what the import raised, the `crc32`, `md5` and `sha256` rows are
  still measured, every xxhash cell reads `-`, and the three panels below the table say what
  was skipped.

All the figures above are **desktop** measurements (Apple M4, macOS 26.6, CPython 3.14.6,
xxhash 3.8.0 from PyPI). The point of running the app is to replace them with the device's
own.

## Try it

[Build](https://flet.dev/docs/publish/) the app, then install it on a device or emulator/simulator:

```bash
# Android
uv run flet build apk

# iOS
uv run flet build ipa

# iOS-Simulator
uv run flet build ios-simulator
```

It also runs on the desktop with `uv run flet run`, which is the fastest way to see the
table before committing to a build.

# xxhash stream digest

One screen that hashes the same generated bytes with `xxh3_64`, `xxh64`, `xxh32` and the three
things Python already has — `zlib.crc32`, `hashlib.md5`, `hashlib.sha256` — at three sizes, then
feeds the largest payload through the streaming API and checks that it lands on the same digest.
Under that, xxHash's own published test vectors recomputed on the device, and two demonstrations
of what a non-cryptographic hash does not protect you from.

The point is the number a page of desktop measurements cannot give you: **what these algorithms
cost on the phone you actually ship to.** Every payload is generated in the app from a fixed
seed rather than bundled, so the same build produces the same bytes on every device and two
phones can be compared with each other.

What it demonstrates:

- **Where xxhash wins, and by how much.** One tap measures all six algorithms over the same
  bytes at 1 KiB, 64 KiB and a payload you pick, and the line under the table prices `xxh3_64`
  against `sha256` and `crc32`. Read the fast rows as ratios rather than absolute rates: above
  roughly 10,000 MB/s the buffer is being re-read out of cache between batches.
- **Where it barely wins, in the row underneath.** `crc32` is the honest competitor — also fast,
  also not tamper-evident — and on a CPU with CRC32 instructions it comes within a fraction of
  `xxh3_64`. Whether a given phone has them is exactly the sort of thing only the device can
  answer, and it is why `crc32` is in the table.
- **What `sha256` actually costs.** Usually not 100×: an arm64 CPU with the ARMv8 SHA-2
  extensions runs it at gigabytes per second, and `md5`, which has no such instructions, ends up
  the slowest row. **An emulator image without those extensions will show `sha256` roughly two
  orders of magnitude slower than a real phone**, which inflates the xxhash ratio into something
  not worth quoting. If your reason for reaching past `hashlib` is "cryptographic hashes are
  slow", this table is where to check that against the hardware you ship on.
- **That the streaming API agrees with the one-shot call, and what it costs.** The chosen
  payload is fed through `xxh3_64().update()` in 64 KiB pieces and compared with
  `xxh3_64_intdigest()` of the whole buffer. They match, and the panel reports both rates —
  XXH3's one-shot entry point has a fast path the incremental state machine cannot use, so
  streaming is the slower of the two and the app says by how much on this device.
- **That the digest is the same everywhere.** 36 of upstream xxHash's own sanity vectors — 8 for
  XXH32, 9 for XXH64, 15 for XXH3-64 and 4 for XXH3-128, chosen to straddle every length branch
  — recomputed over xxHash's own test buffer, which the app regenerates from the two constants
  in `cli/xsum_sanity_check.c`. These are the numbers upstream uses to decide a port is correct,
  so agreement is the claim that this build produces the same bytes as xxHash on any other CPU.
  Both mobile platforms are little-endian, so a device run confirms the vectors but cannot by
  itself demonstrate endianness independence.
- **A collision, found on the device, in milliseconds, with both inputs printed.** A seeded
  birthday search over random 32-byte inputs finds two sharing an `xxh32` digest after 113,202,
  39,741 and 16,915 tries for seeds 0, 1 and 2, and the line underneath shows the pair:
  `0041f8654fe2dbcf…` and `354b0d889ffb06bc…` both hash to `a47caf1d`. Those try counts and that
  pair are identical on every device and every Python, because the generator is seeded — a
  device that prints different ones is telling you something. Only the milliseconds move.
- **The input recovered from the digest.** For an input of exactly four bytes, every step XXH32
  takes is a bijection on 32 bits, so the function is a permutation and can be run backwards
  with arithmetic instead of search. The app inverts 2,000 digests and reports how many came
  back byte-exact; the answer is 2,000. Nothing here is a flaw in xxHash — it is what
  "non-cryptographic" means, and it is the reason a seed is not a key.
- **Degrading instead of crashing.** The import of `xxhash` is guarded. Without the wheel the
  header turns red and names what the import raised, the `crc32`, `md5` and `sha256` rows are
  still measured, every xxhash cell reads `-`, and the panels below the table say what was
  skipped.

`src/digests.py` owns every call into xxhash — the timing harness, the vectors, the birthday
search and the XXH32 inversion — and returns plain values; `src/main.py` is the Flet app around
it. Measurement runs in [`page.run_thread`](https://flet.dev/docs/controls/page/#flet.Page.run_thread)
with the picker locked and a spinner up, and ends with the explicit
[`page.update()`](https://flet.dev/docs/controls/page/#flet.Page.update) a background thread
needs. The example writes no files and opens no sockets — xxhash needs neither.

## Try it

[Build](https://flet.dev/docs/publish/) the app, then install it on a device or
emulator/simulator:

```bash
# Android
uv run flet build apk

# iOS
uv run flet build ipa

# iOS-Simulator
uv run flet build ios-simulator
```

It also runs on the desktop with `uv run flet run`, which is the fastest way to see the table
before committing to a build — but a desktop `flet run` resolves PyPI's wheel, so pin `xxhash`
if you want the same release the device gets. `pyproject.toml` pins both `flet` and `xxhash`,
which is the combination that was verified; `requires-python` stays at `>=3.10`, because
xxhash's own floor is `>=3.8` and every split uv resolves for is satisfiable.

# duckdb readings warehouse

A million sensor readings living in a DuckDB database file on the phone. Three analytical
queries run over them on demand, and an Export button writes the whole table out as
[Parquet](https://duckdb.org/docs/current/data/parquet/overview.html) and reads it straight
back. Nothing is bundled and nothing is downloaded: the rows are generated by the engine
itself on first launch, so every install holds the same data and two devices can be
compared number for number.

What it demonstrates:

- **The settings a mobile connection needs, passed at
  [`connect`](https://duckdb.org/docs/current/clients/python/overview.html) rather than
  afterwards** — a `memory_limit` (the default is 80% of the device's *total* RAM), a thread
  count, a `temp_directory` pointing at
  [`FLET_APP_STORAGE_TEMP`](https://flet.dev/docs/reference/environment-variables/#flet_app_storage_temp),
  and extension
  [autoinstall/autoload](https://duckdb.org/docs/current/extensions/overview.html#autoloading-extensions)
  turned off so a mistyped function name cannot become a network fetch.
- **A database that survives restarts** — the file goes in
  [`FLET_APP_STORAGE_DATA`](https://flet.dev/docs/reference/environment-variables/#flet_app_storage_data),
  and a relaunch finds the table already populated instead of rebuilding it.
- **Work the engine does that Python cannot afford** — a
  [window function](https://duckdb.org/docs/current/sql/functions/window_functions.html)
  computing a 60-point moving average over a million rows, `quantile_cont` percentiles, and
  hourly bucketing with `date_trunc`, each reporting its own elapsed milliseconds.
- **A Parquet round trip** — `COPY … (FORMAT PARQUET, COMPRESSION zstd)` out to app storage
  and `read_parquet(…)` back in, with the Parquet and database file sizes side by side.
- **Queries on [`page.run_thread(...)`](https://flet.dev/docs/controls/page/#flet.Page.run_thread)
  with a working Cancel** — `con.interrupt()` aborts the running query, and the worker is
  wrapped so the resulting `InterruptException` is reported rather than swallowed, plus the
  explicit [`page.update()`](https://flet.dev/docs/controls/page/#flet.Page.update) a
  background thread needs. Never two workers at a time, either — `run_thread` hands work to a
  thread *pool* and would happily run two, and disabling the controls cannot catch a tap
  already in flight, so a non-blocking lock is what keeps the one shared connection legal.
  Two threads executing on one connection object cross each other's results instead of
  raising; see the recipe's [Threading](../../README.md#threading).
- **Which engine you are actually talking to** — the header prints DuckDB's own platform
  string, the extensions compiled into the wheel, and the limits the connection opened with.

`[tool.flet.android] target_arch` restricts the build to the two 64-bit ABIs. That is a
choice, not a requirement — an `armeabi-v7a` wheel does exist — but each ABI carries its own
47–62 MB copy of the engine, so a default three-ABI build triples the largest thing in the
artifact.

## Try it

[Build](https://flet.dev/docs/publish/) the app, then install it on a device or emulator:

```bash
uv run flet build apk
```

`flet run` works too: the same pins resolve on desktop, where PyPI serves duckdb at that
version, and the app makes no mobile-only assumptions.

Read the recipe's [iOS notes](../../README.md#ios-notes) before trying `flet build ipa` or
`flet build ios-simulator`: the iOS wheels currently on the index are expected to fail at
link time, for a reason that has nothing to do with this app.
